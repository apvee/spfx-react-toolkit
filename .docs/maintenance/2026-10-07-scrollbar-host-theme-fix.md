# Actual SharePoint host scrollbar colors — 2026-10-07

User reported that the colors still did not change after the local-browser hover correction. Inspection of the actual authenticated Edge workbench established a different cause: in **host** mode all three CSS variables were `#605e5c`. The installed Fluent v8→v9 migration shim maps base/hover/pressed accessible neutral stroke tokens to the same v8 `neutralSecondary` value. Standard demo themes had distinct colors, so the earlier local checks did not cover this real converter/provider case.

`createFluent9ThemeFromSPFxTheme` now preserves the shim's base and other converted tokens, while mapping accessible stroke hover to host `neutralPrimary` and pressed to `neutralDark`. Empty/missing values retain the shim's fallback. Undefined webLightTheme identity, Teams theme identities, source-theme immutability, public signatures/peers and 6px/3px geometry remain unchanged. Real converter and real sample-host-provider regression tests failed before the fix and passed afterward; light/custom dark/fallback/nonmutation/other-token preservation covered. JSDoc and public helper/style documentation were updated.

Fresh build/verify/package passed: **676 tests**, complete36 bundle/18 runtime/nine mutation gates and strict independent consumer commands. Independent source review had no findings. The known repository app gulp serve was restarted, and the user's existing Edge workbench was reloaded without saving/publishing tenant content.
